NIM 검사는 승인된 기존 키를 일시적으로 프로세스에 주입했다. 키를 이미지·저장소에 넣지 않았다.
한 케이스 실행 안에서 자동 재시도가 발생했으며, 별도의 추가 케이스는 실행하지 않았다.
브라우저 검사는 규칙 폴백 경로이며 NIM CLI 검사와 별개다.
오류 발췌·재현 조건·영향은 [알려진 문제](KNOWN_ISSUES.md)에 남겼다.

### NVIDIA NIM 실호출 (2026-09-25)

실제 `nat serve`(CuAlignWorker → PlanEventsASGI + Guardrails + NIM)를 띄우고 UI와 같은 방식으로
`/chat/stream`을 두 번 호출했다. 모델은 `configs/workflow.yml` 기준 `nvidia/nemotron-3-super-120b-a12b`,
Guardrails는 키가 있어 자동 활성화됐다. 키는 `.env`에서만 읽었고 로그·이미지에 넣지 않았다.
이벤트 전문과 서버 로그는 추적 제외된 `out/nim-live/`에 있다.

**먼저 발견한 결함.** 첫 실행이 4.5초 만에 빈 응답으로 끝났다. `additional_instructions`의 리터럴
`{"plan_id": "..."}`를 LangChain `ChatPromptTemplate`이 템플릿 변수로 해석해
`Input to ChatPromptTemplate is missing variables {'"plan_id"'}`로 에이전트 노드가 죽었다.
`nat validate`는 프롬프트를 만들지 않아 이 결함을 잡지 못한다. 중괄호를 없애고,
실제 프롬프트를 만들어 변수 집합을 확인하는 오프라인 회귀 검사를 추가했다.

| 확인 항목 | 1턴 `발치 없이 12개월 안에, 앞니 총생부터` | 2턴 `13번 치아는 움직이지 말고 다시 짜줘` |
|---|---|---|
| 소요 | 86.2초 | 59.6초 |
| `plan_selected` 이벤트 | 수신. `request_id`·`case_id` 일치 | 수신 |
| 부모 이력 | `parent_plan_id` 없음(최초) | 1턴 계획을 부모로 기록 |
| 규칙 결과 | 통과. expansion_ipr 14단계 | 통과 |
| 조건 유지 | 비발치·`stage_cap` 52·`anterior_first` 유지, 발치 치아 0개 | `lock:[13]` 적용, 비발치·상한·순서 그대로 유지 |
| 고정 치아 | — | 전 단계에서 13번 변위 0 확인 |
| 검토 | **2회 시도 후 성공**. 한국어 검토 메모 생성 | **2회 시도 후 실패**, `upstream_503` 저장 |
| 승인 | 승인 전 다운로드 409 → 승인 200 → 다운로드 200 (17.7MB) | 새 계획이라 승인 초기화(`approval: null`) |

두 턴 모두 검토를 **2회 안에** 끝냈다. 2턴의 `upstream_503`은 NVIDIA 엔드포인트에서 실제로 발생했고,
상한에서 멈춰 실패 상태를 저장했으며 에이전트는 최종 답변에 `검토 실패 — ... (시도 2회, 오류: upstream_503)`를
그대로 적었다. 메모를 지어내거나 재호출 루프에 빠지지 않았다.
이관 기록에서 관측된 무한에 가까운 reviewer 재시도는 재현되지 않았다.

Guardrails 입력 레일은 두 턴 모두 통과했고(`triggered_input_rail: None`) 원격 판정 경로가 실제로 실행됐다.
1턴에서 NAT의 ReAct 출력 파싱 재시도가 1회 있었으나 같은 턴에서 복구했다.

**정정:** 최초 기록에서 `intermediate_data`가 오지 않는다고 적었으나 이는 검증 스크립트의 파서 오류였다.
NAT는 SSE 필드 이름 자체를 `intermediate_data:`로 보내는데 스크립트가 `event:`/`data:`만 읽어 버렸다.
실제로는 요청당 13~59개가 도착하며 브라우저의 도구 추적도 정상 동작한다. 파서를 고쳤다.

### 브라우저 실사용에서 드러난 결함 (2026-09-25)

위 스크립트 검증을 통과한 뒤 브라우저에서 직접 대화해 보니 대부분의 요청이 실패했다.
같은 요청을 반복해 재현하니 **3회 중 1회만** 계획을 만들었다. 원인은 세 가지였다.

| 증상 | 원인 | 수정 |
|---|---|---|
| `set_constraints` 70회 반복 후 iteration 상한(26)에서 종료 | 모델이 바꾸지 않는 필드에 채우는 `null`을 치명적 오류로 처리 | `null`·생략은 유지, 해제는 `[]`와 `clear_stage_cap` |
| `set constraints before generating targets` 반복 | 값이 바뀌지 않는 재호출도 무조건 거부 | 결과가 같으면 no-op으로 현재 조건 반환 |
| 빈 응답 → `ReActAgentParsingFailedError` | 엔드포인트 503과 부족한 재시도 | `num_retries` 1→5(NAT 기본값), `parse_agent_response_max_retries` 2→4 |

첫 두 결함은 **오프라인 검사 40개가 모두 통과하는 상태에서** 발생했다.
검사가 `ConstraintPatch` 객체를 직접 만들어 넘겨 NAT의 스키마 왕복을 건너뛰었기 때문이다.
실제 도구 호출은 스키마의 모든 필드가 채워진 채 도착해 `exclude_unset`이 무력화된다.
세 결함 모두 회귀 검사를 추가했고, 그중 하나는 딕셔너리로 도구를 호출해 실제 경로를 지난다.

같은 요청을 반복해 측정한 결과는 수정 전 **1/3**, null 계약만 고쳤을 때 **3/4**,
두 루프와 재시도를 모두 고친 뒤 **5/6**이다. 파싱 실패와 iteration 초과는 0건이 됐고
`set_constraints` 호출이 요청당 1회 수준으로 내려갔으며 503 2건은 재시도로 흡수됐다.
성공한 6회 중 1회는 검토가 503으로 실패했고 승인이 막히는 설계대로 동작했다.

남은 실패 1회는 에이전트가 목표 생성 뒤에 조건을 **실제로 바꾸려다** 거부당한 경우다.
조건 고정은 의도한 동작이므로 거부 자체는 유지하되, 이때 계획 없이 대화를 끝내는 일이 있다.
소수 표본이므로 위 비율을 안정적인 성공률로 해석하지 않는다.

### 이번에 실행하지 않은 검사

- Docker 빌드·실행, Linux/macOS에서의 실호출 재현.
- 장시간·다회차 성공률: 503은 원격 상태에 따라 달라지므로 소수 실행으로 안정성을 단정하지 않는다.
- 나머지 3개 시나리오(비교·되묻기·규칙 실패)의 실호출과 `scripts/run_scenarios.py` 갱신.
- 503은 원격 상태에 따라 달라지므로 위 결과가 매 실행의 성공률을 뜻하지 않는다.
- 재시작 복원·사용자 인증·다중 사용자 격리는 이번 구현 범위가 아니다.

## 재현 범위

현재 지원 경로는 **저장소 체크아웃에서 설치·실행**이다. 서버와 벤치마크는 패키지 밖 `configs/`, `guardrails/`, `bench/`도 사용한다.
정적 자산이 wheel에 포함됐다는 사실만으로 wheel 단독 서비스 배포가 지원된다고 해석하지 않는다.
