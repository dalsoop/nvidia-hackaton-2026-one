# 알려진 문제와 후속 확인

> 2026-09-25. 아래 구현 상태와 실제 NVIDIA 실호출 검증 여부를 구별한다.

## reviewer 빈 응답·ReAct 파싱 반복

2026-09-24 이관 코드의 Docker Linux arm64/NIM 실행에서 reviewer 빈 응답과
`ReActAgentParsingFailedError`, 도구 재시도 소진 후 상위 에이전트 재호출이 관측됐다.
계획 계산은 성공했으나 최종 검토 메모를 얻기까지 89.5초가 걸렸다.
당시 기록은 [VERIFICATION](VERIFICATION.md)에 보존한다.

현재 reviewer는 읽기 전용 계획 요약에 대한 제한된 NIM 호출로 교체했다.
ReAct 검토 루프는 사용하지 않으며 최대 2회, 호출당 20초, 전체 40초 후 실패 상태를 저장한다.
같은 결과의 재호출은 저장된 결과를 반환한다. 실패를 UI에서 표시하고 승인을 막는다.
빈 응답·503·잘못된 응답·타임아웃 주입 검사를 추가했다.

**2026-09-25 실호출 확인.** 실제 서버·NIM으로 2턴을 실행했다. 1턴은 2회 시도 후 검토 메모를 받았고,
2턴은 2회 시도 후 `upstream_503`으로 실패해 상태를 저장하고 승인을 막았다.
에이전트는 실패를 최종 답변에 그대로 적었고 재호출 루프에 빠지지 않았다.
이관 기록의 무한에 가까운 재시도는 재현되지 않았다. 결과는 [VERIFICATION](VERIFICATION.md) 참조.

**남은 불확실성:** 503은 원격 상태에 따라 달라지므로 1회 실행으로 발생률을 말할 수 없다.
[PR #10](https://github.com/dalsoop/nvidia-hackaton-2026-one/pull/10)의 스트림 503→빈 답변과
같은 근본 원인인지도 확정하지 않는다. 확인된 것은 503이 지금도 발생하며 상한 안에서 처리된다는 점이다.

재현 입력: `moderate 케이스로. 발치 없이 12개월 안에 끝나는 계획 짜줘. 앞니 총생부터 풀고.`
모델은 configs/workflow.yml 기준이다. 키와 환자 데이터는 로그에 넣지 않는다.

## ReAct 지시문의 중괄호

`additional_instructions`에 리터럴 중괄호를 쓰면 LangChain `ChatPromptTemplate`이 템플릿 변수로 읽어
에이전트가 첫 호출에서 죽는다. 2026-09-25 실호출에서 `{"plan_id": "..."}` 때문에 실제로 발생했다.
`nat validate`는 프롬프트를 만들지 않아 잡지 못하므로
`tests/test_stack_offline.py`의 `test_react_prompt_has_no_stray_template_variables`로 검사한다.
지시문을 고칠 때 중괄호를 넣지 않는다.

## 조건 패치의 null 계약

에이전트는 바꾸지 않는 필드에 `null`을 채워 보낸다. 초기 구현은 `exclude_unset`에 기대어
`null`을 오류로 처리했는데, 도구 호출은 스키마의 모든 필드를 채워서 도착하므로 사실상 모든
`set_constraints` 호출이 실패했다. 오류에 복구 경로가 없어 ReAct 에이전트가 같은 호출을
반복하다 iteration 상한(26)에서 죽었다. 2026-09-25 브라우저 실호출에서 관측했다.

오프라인 검사는 `ConstraintPatch`를 직접 만들어 넘겼기 때문에 이 경로를 지나지 않았고 통과했다.
지금은 `null`과 생략이 모두 "유지"이고, 해제는 `[]`와 `clear_stage_cap: true`로만 한다.
모든 필드를 `null`로 채운 도구 호출을 재현하는 검사를 추가했다.
도구 입력 계약을 바꿀 때는 딕셔너리로 호출하는 검사를 함께 둔다.

## 검토를 호출하지 않고 끝나는 턴

6회 측정 중 1회에서 에이전트가 `select_plan` 뒤 reviewer를 호출하지 않고 답변을 끝냈다.
계획의 검토 상태는 `not_requested`로 남고, 승인은 `passed`/`skipped`만 허용하므로 막힌다.
화면에는 계획과 3D가 보이지만 승인·다운로드로 진행할 수 없고 다시 요청하는 것 외에 방법이 없다.

의도한 차단(검토 실패)과 달리 이것은 에이전트가 절차를 건너뛴 경우다.
같은 계획을 수동으로 재검토하는 수단이 없어서 막다른 길이 됐다.

지금은 두 겹으로 막는다.
- 에이전트가 계획을 고르고 검토 없이 턴을 끝내면, 서버(`plan_events.py`)가 `plan_selected` 를 보내기 전에 같은 reviewer 설정
  (시도·시간 상한)과 모델로 그 계획을 검토한다. 이벤트의 `reviewed_by_server: true` 와 화면 안내, 서버 WARNING 로그로 남는다.
  모델이 절차를 지키는지에 기대지 않는다. 그만큼 그 턴의 끝이 검토 시간(최대 40초 + 메모 레일 판정)만큼 늦어진다.
- 검토가 `not_requested`·`failed` 인 계획에는 «검토 다시 요청» 버튼이 보이고, 의사가 누르면 `POST /api/plans/{id}/review` 가
  같은 설정으로 다시 검토한다. 에이전트 경로는 여전히 저장된 실패를 돌려주므로 모델 반복 호출은 막힌다.
  `passed`·`skipped` 는 다시 부르지 않는다(409). 에이전트가 받은 실패는 서버가 덮어쓰지 않는다.

검토 메모는 답이 아니라 계획 카드로 나가므로, 전에는 출력 레일을 거치지 않았다(에이전트 경로·재요청 모두).
지금은 reviewer 가 메모를 저장하기 전에 답과 같은 출력 검사(처방 문구 목록 → 출력 레일 모델)를 거친다(`reviewer.MEMO_CHECK`).
막힌 메모는 저장하지 않고 다음 시도로 넘어가며, 다 쓰면 `failed`·`rail_blocked` 다. 레일 오류는 답과 같은 정책을 따른다
(기본은 통과시키고 `rails: "error"` 를 남김, `CUALIGN_RAILS_FAIL_CLOSED=1` 이면 `rail_error` 로 실패). 레일이 꺼져 있으면 `rails: "off"` 다.
`nat run`·`cualign plan` 에는 HTTP 요청 경로가 없어서 서버의 검토 대체 실행이 돌지 않는다.

## 스트림 503 이 빈 답이 되는 문제

NVIDIA API 는 과부하일 때 스트림 요청에 HTTP 200 과 오류 한 줄
(`{"error": {"message": "Service temporarily overloaded", "code": 503}}`)만 보내고 닫는다.
`langchain-nvidia-ai-endpoints` 1.4 는 `"object": "error"` 가 붙은 오류만 예외로 만들어서, 이 줄은 내용 없는 메시지가 된다.
NAT 의 LLM 재시도는 예외만 보므로 돌지 않는다. ReAct 에이전트는 빈 글을 형식 오류로 읽고 곧바로 다시 묻다가,
파싱 재시도(4회)를 다 쓰면 턴을 끝낸다. 원인과 재요청 방식은 hoddukzoa12 의
[PR #6](https://github.com/dalsoop/nvidia-hackaton-2026-one/pull/6) 실측을 따랐다
(모델 호출의 24~31% 가 이 503, 재요청으로 빈 답 턴 9개 → 1개).

지금은 `agent/nim_stream_patch.py` 가 스트림의 첫 메시지가 재시도할 오류(429·5xx)이면 1·2·4·8·16·32초 뒤 다시 요청한다.
다 쓰거나 재시도할 수 없는 오류면 빈 답 대신 `NIMStreamError` 로 턴을 끝낸다. 그래서 모델 호출 하나가 최대 약 63초 늦어질 수 있다.
API 오류 내용은 로그에만 남기고 예외 문구에는 싣지 않는다. NAT 재시도는 문구에 «429» 가 있으면 호출 전체를 다시 돌리기 때문이다.
이미 내용이 온 뒤 스트림 중간에 오는 오류는 다루지 않는다(관측되지 않음).
계획 에이전트(ReAct)는 스트림으로 부른다. 스트림이 아닌 호출은 같은 과부하를 진짜 HTTP 상태로 받는다([#34](https://github.com/dalsoop/nvidia-hackaton-2026-one/issues/34)).
- 검토 호출(`reviewer.py` 의 `ainvoke`)은 라이브러리가 `[503] …` 예외로 바로 던지고, 그 위에서 다시 부르는 곳이 없다(NAT 재시도는 예외의 속성이나
  첫 인자에서만 상태 코드를 읽고, `nim_review` 는 `num_retries: 1` 이다). 지금은 같은 모듈이 이 호출도 429·5xx 이면 1·2·4초 뒤 다시 요청하고
  (최대 4회 · 기다림 7초 · 검토 호출당 20초 예산 안), 다 쓰면 원래 예외를 그대로 던진다. 검토는 그 문구의 «503» 으로 `upstream_503` 을 적는다.
- 레일 판정은 이 모듈을 거치지 않는다. NeMo Guardrails 0.24 는 `engine: nim` 을 `ChatNVIDIA` 가 아니라 자체 OpenAI 호환 클라이언트로 부르고,
  그 클라이언트가 429·5xx 를 0~0.5·2ⁿ초(최대 8초) 무작위 대기 뒤 다시 묻는다. 기본 재요청은 2회뿐이라 9/25 실호출에서 그보다 오래 간 503 이
  레일 판정 하나를 떨어뜨렸다. 지금은 `guardrails/config.yml` 이 두 모델 모두 `max_retries: 4` 로 둔다(기다림 최대 7.5초 · 판정 25초 예산 안).
25초 시간 제한에 걸리는 레일 판정은 이것으로 줄지 않는다. 범위 판정 레일이 계획 모델과 같은 120B 모델을 쓰기 때문이다(`guardrails/config.yml`).

## 같은 도구를 반복 호출하다 멈추는 턴

2026-09-25 실호출에서 비교 시나리오가 `set_constraints` 를 24번 넘게, 2턴 수정이 `get_constraints` 를 27번 같은 인자로 불러
반복 상한에서 끝났다. NAT 1.9 ReAct 의 네이티브 도구 호출 모드는 다음 프롬프트를 앞선 호출의 생각 글(`AgentAction.log`)과
도구 결과로만 만든다. 생각 글이 «먼저 X 를 불러야 한다» 뿐이거나 비어 있으면(`Calling X`) 어떤 도구를 어떤 인자로 불렀는지가
빠지므로, 모델이 이미 부른 것을 모르고 다시 부른다(`nat/plugins/langchain/agent/react_agent/agent.py` 의 `agent_node`).

지금은 `agent/react_history_patch.py` 가 새로 생긴 기록마다 실제로 실행한 `Action`·`Action Input` 을 붙인다.
NAT 의 기록 형식·파싱·재시도는 그대로이고, 반복 호출을 막거나 도구 성공을 주장하지는 않는다. 한 응답에 도구 호출이 여럿이면
NAT 가 첫 호출만 실행하므로 그 하나만 기록된다. NAT 를 올릴 때 `agent_node` 가 바뀌면 이 패치를 다시 확인한다
(`tests/test_react_history.py` 가 패치 없이 실패하는 것을 확인했다).
