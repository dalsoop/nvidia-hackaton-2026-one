# 개발 시작 안내

이 저장소는 팀이 이어서 개발할 수 있는 실행 가능한 PoC다. 완성된 제품이나 확정된 팀 아키텍처를 넘기는 것이 아니다.
이미 있는 계산·도구·UI·데이터·검증을 출발점으로 쓰고, 변경할 부분은 팀이 정한다.

## 처음 받았을 때

1. [아이디어 소개](OVERVIEW.md)와 [PRD](PRD.md)로 문제와 예선 목표를 파악한다.
2. [README 실행 안내](../README.md)의 키 없는 명령을 실행한다. 기대 결과는 테스트 39개 통과와 moderate 병행안 14단계다.
3. `uv run cualign serve --host 127.0.0.1`로 UI를 열고 moderate 샘플을 선택한다. 키가 없어도 규칙 기반 버튼으로 3D 단계·다운로드를 살펴볼 수 있다. 대화는 NIM 키가 필요하고 three.js 로딩에는 네트워크가 필요하다.
4. [TRD](TRD.md)로 계산·상태의 한계를 읽고, [코드 안내](CODE_MAP.md)에서 작업할 모듈을 찾는다.
5. [알려진 문제](KNOWN_ISSUES.md)와 [검증 기록](VERIFICATION.md)을 보고 아래 작업 후보를 팀 계획으로 구체화한다.

CLI의 “앞니 먼저” 요청과 UI 규칙 버튼의 기본 동시 이동은 다른 입력이다. 단계 수가 다른 것 자체는 오류가 아니다.
모델 키는 각자 로컬 환경에서 설정하며 공유하거나 커밋하지 않는다.

## 이번 예선 개선 작업

조건 수정 후 3D 연결 → 공통 제약 유지 → reviewer 오류 처리 → 의사 승인·내보내기 순서의
네 기능을 같은 브랜치에서 구현한 범위와 검증 방법은 [예선 데모 개선 작업](ROADMAP.md)에 정리한다. 실제 NIM 검증과 오프라인 검증을 구별한다.

## 개발 계획의 출발점

아래는 현재 간격에 근거한 작업 후보다. 담당 배정·스프린트·일정·구현 방식을 정한 것은 아니다.
공통 조건·계획 식별·화면 상태의 최소 계약을 함께 정하면 에이전트, 계산/API, UI 작업을 나눠 진행하기 쉽다.

| 작업 후보 | 먼저 볼 코드·문서 | 완료를 확인할 장면 |
|---|---|---|
| 검토 에이전트 안정성 | KNOWN_ISSUES의 reviewer 항목, `configs/workflow.yml`, `agent/react_patch.py` | 검토 실패를 성공으로 숨기지 않고 유한한 재시도 뒤 결과 또는 오류를 표시 |
| 조건 유지·비교·수정 | TRD §4, `agent/register.py`, `core/store.py`, `core/planner.py` | 비발치·고정 치아·IPR 제외가 비교와 수정 뒤에도 같은 조건으로 계산·검증됨 |
| 결과 API·화면 일치 | `server/api.py`, `server/static/app.js`, `core/store.py` | 선택 케이스·계획·3D·다운로드가 일치하고 실패·검토 상태를 구분 |
| 대화·3D 검토 UX | PRD §5–7, `server/static/`, DESIGN_REFERENCES | 통과·실패·비교·되묻기·수정을 사용자가 이해하고 다음 행동을 선택 |
| 통합 검증·시연 준비 | VERIFICATION, `tests/`, `scripts/run_scenarios.py`, NVIDIA_STACK | 실제 UI 대화에서 다섯 시나리오와 모델·검사 오류 경로를 확인하고 새 실행 증거 보존 |

코드 경로는 별도 표기가 없으면 `src/cualign/` 아래다. 조건 유지와 결과 식별 변경은 UI·에이전트 양쪽에 영향을 주므로 인터페이스를 먼저 공유한다.
UI/UX는 화면·상태·문구 설계를 맡고 개발자는 구현 방식을 선택할 수 있다. 임상 적합성은 어느 한 개발 역할의 판단으로 대체하지 않는다.

## 합의가 필요한 것과 지금 시작할 수 있는 것

- 제품 동작: [PRD §7](PRD.md#7-팀-검토가-필요한-세부-동작)에만 결정 목록을 유지한다. 비교 시작 방식·검토 확정·실패안 출력 등의 정책은 관련 담당과 결정한다.
- 운영 범위: 로컬 단일 사용자 시연을 넘길지, 검사 불가 시 어떻게 처리할지는 TRD §4–5와 SECURITY를 바탕으로 합의한다.
- 기술 선택: 현 구현을 바로 실행·분석하고 테스트를 보강할 수 있다. 새 스택 채택이나 전체 재작성은 착수의 전제조건이 아니다.
- 대회 확인: [NVIDIA_STACK](NVIDIA_STACK.md)의 ‘Skill API’ 인정 범위는 미확정이다. 제출 전 확인할 항목이며 내부 개발을 멈출 이유는 아니다.
- 세그먼테이션·장치 셸 생성·직접 3D 조작은 별도 검토다. 예선 핵심 흐름 개발을 막는 선행 작업으로 두지 않는다.

## 샘플·자료는 어디 있나

| 자료 | 위치·사용 방법 |
|---|---|
| 실행용 치아 형상 | `src/cualign/core/templates/`의 STL 14개와 ATTRIBUTION. 저장소에 포함되므로 데모용 메시를 따로 구할 필요 없음 |
| 합성 케이스 | `core/synth.py`에서 생성. 파일로 필요하면 `uv run cualign cases build --out data/cases` |
| 과거 실행·비교 자료 | `docs/demo/`, `docs/model-swap.md`, `bench/results.md`. 현재 버전 검증은 VERIFICATION과 구별 |
| UI·형상 조사 | DESIGN_REFERENCES의 관찰·원문 링크. 외부 제품 이미지·원본 메시 전체를 재배포한 묶음은 아님 |
| NVIDIA 관련 자산 | `configs/`, `guardrails/`, `openshell/`, `skills/`. 각 자산의 실제 연결 수준은 NVIDIA_STACK 참조 |

## 작업을 인계할 때

선택한 작업의 목적, 관련 PRD/TRD 항목, 수정할 모듈, 관찰 가능한 완료 기준, 실행할 검증을 PR이나 이슈에 적으면 된다.
테스트 명령은 [CONTRIBUTING](../CONTRIBUTING.md)에 모아 두었다. 모든 문서를 복제하거나 개인 작업 관리 방식을 도입할 필요는 없다.
새 요구사항은 PRD, 기술 구조·계약 변화는 TRD, 재현 결과는 VERIFICATION에 반영한다.
