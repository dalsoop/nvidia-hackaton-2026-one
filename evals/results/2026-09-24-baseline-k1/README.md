## 빈 응답의 원인 (후속 진단, 같은 날)

에이전트 로직이 아니라 **NVIDIA API 과부하(503)가 빈 답변으로 바뀌어 전달된 것**이다.

- 서버는 HTTP 200 스트림의 첫 줄에 `{"error": {"message": "Service temporarily overloaded", "code": 503}}`만 보내고 닫는다.
- `langchain-nvidia-ai-endpoints`의 스트림 처리(`_NVIDIAAsyncClient.aget_req_stream`)는 스트림 안의 오류를 예외로 만들지 않는다.
  그래서 내용 없는 메시지가 되고, NAT ReAct는 이를 형식 오류(`LLM output: ''`)로 보고 대기 없이 파싱만 3회 재시도한 뒤 턴을 끝낸다.
- 측정한 빈도: 모델 호출의 24~31%가 이 503이었다. 토큰 한도(`finish_reason: length`)에 걸린 호출은 1건뿐이었다.
- NAT의 LLM 자동 재시도(503 포함, 지수 대기)는 이 경로에서 작동하지 않았다. 스트림 오류를 예외로 바꿔도 재시도 기록이 없었다.
- 확인한 대응: 스트림 첫 줄이 오류이면 1·2·4초… 간격으로 최대 6회 다시 요청했다. 이 방식으로 이 표의 중단 명세 6개를 다시 돌리자
  빈 답변 턴이 9개 중 1개로 줄었다(503 41건 중 32건은 첫 재요청에서 회복, 1건은 6회 모두 소진).
  같은 실행에서 A04·A05·A15는 통과했다(각 1회).

따라서 이 표의 S0 거부 6건은 에이전트 품질이 아니라 API 가용성 문제로 읽어야 한다.

## 이 결과를 읽을 때

- **각 명세 1회 실행이다.** 합격 판정(pass^k)은 3회 반복이 기준이며, 이 표의 통과·실패에는 우연이 섞여 있을 수 있다.
- **ReAct 파싱 재시도 횟수는 실제보다 적게 기록됐다.** 실행 당시 실행기는 NAT의 INFO 로그를 받지 못했다(이후 `4b066da`에서 수정). 중단된 턴의 오류 메시지에는 재시도 소진이 그대로 남아 있다.
- **HTTP 계층의 Guardrails는 거치지 않았다** (`nat run`과 같은 경로).
- **측정 중 판정기 오탐 3건을 고쳤다.** 모두 실제 모델 출력으로 처음 드러났고, 회귀 예문을 `tests/test_golden_a_checks.py`에 추가했다.
  - 메모 끝 고정 문구를 뺀 경우 (A02)
  - 같은 줄의 확장 수치를 IPR 수치로 읽은 경우 (A18)
  - 여러 턴에서 이전 턴 메모·검증을 인정하지 않고, 소수점 표기(2.9 / 2.90)를 다르게 본 경우 (A16)
